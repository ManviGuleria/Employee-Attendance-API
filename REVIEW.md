# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `list_employees` — `skip = page * page_size` | Off-by-one in pagination. With `page=1` and `page_size=20`, the starter skips 20 records and returns results starting at row 21, so the first page is always empty. | `GET /employees?page=1` returns no items even when employees exist. | Changed to `skip = (page - 1) * page_size`, matching R10 ("page starts at 1"). |
| 2 | `list_employees` — no `.sort()` call | Results are returned in MongoDB natural order (insertion order), not sorted by `emp_code` ascending as the OpenAPI spec requires. | Two consecutive calls may return employees in different orders; a client relying on sorted output gets wrong data. | Added `.sort("emp_code", ASCENDING)` to the query cursor. |
| 3 | `list_employees` — `total = db.employees.count_documents({})` | `total` ignores the `department` filter, so it always reports the count of every employee in the database, not the filtered set. | `GET /employees?department=Engineering` returns `total=6` when only 2 employees are in Engineering. | Changed to `db.employees.count_documents(q)`, where `q` already holds the filter. |
| 4 | `punch_in` — `ts = datetime.fromtimestamp(body.punched_at / 1000)` | `datetime.fromtimestamp()` produces a **naive** datetime in the local system timezone, not UTC. Subsequent comparisons and storage are inconsistent with UTC-aware datetimes and other parts of the code. | On a machine set to IST, a `punched_at` of `1783312500000` stores a time 5h30m ahead of what was intended. | Used `ms_to_dt()` which calls `datetime.fromtimestamp(s, tz=timezone.utc)`, returning a timezone-aware UTC datetime; also truncates to whole seconds (R1). |
| 5 | `punch_in` — attendance date computed as `ts.date().isoformat()` | The date is derived from the naive local datetime, not from the IST wall-clock. For an employee punching in at 23:00 IST, the stored `date` could be the next UTC calendar day, breaking the attendance record entirely. Overnight-shift logic (R1) is also missing. | An employee with an overnight shift (e.g. 22:00–06:00) punching in at 23:00 IST gets a `date` one day ahead of the correct attendance day. | Replaced with the `attendance_date()` helper that converts to IST and handles the overnight-shift case per R1. |
| 6 | `punch_in` — `db.employees.find_one(…)` result not checked for `None` | If an unknown `emp_code` is supplied, `emp["shift_start"]` raises `TypeError: 'NoneType' is not subscriptable`, returning a 500 instead of the required 404. | `POST /attendance/punch-in` with `emp_code="BADCODE"` crashes with a 500. | Added an explicit `if not emp: raise HTTPException(404, …)` guard. |
| 7 | `punch_in` — race condition: check-then-insert pattern | The code does a `find_one` to detect duplicates and only then calls `insert_one`. Between those two operations a second concurrent request can also pass the check and both inserts succeed, creating two records for the same `(emp_code, date)`. | Sending two simultaneous punch-in requests for the same employee on the same date results in two 201 responses and two documents. | Removed the pre-check; rely solely on the unique compound index `(emp_code, date)` and catch `DuplicateKeyError` to return 409. This makes the duplicate-prevention atomic. |
| 8 | `compute_late_minutes` — wrong time calculation | The function uses `punch_in.replace(hour=h, minute=m, …)` to build `shift_start`. Because `punch_in` is a naive datetime (see bug 4), `.replace()` keeps whatever timezone offset the system has, so the difference is wrong. Even with correct UTC datetimes the replace approach is broken—the shift starts at `shift_start` **IST on the attendance day**, not by replacing the hour of the punch-in UTC instant. | Punch-in at 09:28 IST correctly returns `late_minutes=0`, but punch-in at 09:41 IST (11 min late) might return 0 or a wrong value depending on the server timezone. | Rewrote `compute_late_minutes` to construct the shift-start as a proper IST datetime for the correct calendar day, convert to UTC, then diff. |
| 9 | `compute_overtime` — wrong shift-end datetime construction | The function does `datetime.fromisoformat(date_str).replace(hour=h, minute=m, tzinfo=IST)`. `datetime.fromisoformat("2026-07-06")` returns a `date` not a `datetime` in Python < 3.11 and `datetime` with no time in 3.11+; `.replace(tzinfo=IST)` on a `date` object raises `AttributeError`. Even if it didn't, overnight shifts (where the shift end falls on the next calendar day) are not handled. | On Python 3.10 or earlier, `POST /attendance/punch-out` raises `AttributeError`. On 3.11+, overnight shifts compute a wildly incorrect overtime value. | Rewrote as `compute_overtime_minutes_full()` which takes `shift_start` to detect overnight shifts and sets the end time on `attendance_day + 1` when appropriate. |
| 10 | `list_attendance` — loads entire collection into memory | The code calls `list(db.attendance_logs.find(q))`, fetching all matching documents, sorts them in Python, counts them, then slices for the page. On a large collection this is extremely slow and will OOM the process. The OpenAPI spec explicitly says "must stay fast on ~100,000 records; do not load into memory". | With 100k records, the endpoint times out or crashes. | Changed to server-side sort (`.sort([("date", DESCENDING), ("emp_code", ASCENDING)])`), then `.skip()` / `.limit()` on the cursor, with a separate `.count_documents(q)` for `total`. |
| 11 | `create_employee` — `datetime.now()` without timezone | `doc["created_at"] = datetime.now()` produces a naive datetime. Stored as BSON it is treated as UTC by PyMongo, but when serialised the API should return epoch milliseconds (per the Employee schema). The starter returns the raw `datetime` object, which FastAPI serialises as an ISO string, not epoch ms. | `POST /employees` response has `created_at: "2026-07-06T10:00:00"` (string) instead of an integer epoch ms value. | Changed to `datetime.now(tz=timezone.utc)` and passed through `serialize_employee()` which calls `dt_to_ms()`. |
| 12 | `list_attendance` — `d["id"] = str(d.pop("_id"))` leaks `_id` as `id` | The OpenAPI spec says `_id` is internal and must never appear in a response. Renaming it to `id` exposes the internal MongoDB ObjectId under a different key. No `id` field exists in `AttendanceRecord`. | `GET /attendance` returns an `id` field in each item that the spec does not define; automated graders checking for exact schema fail. | Replaced with `serialize_record()` which simply pops `_id` with no renaming, and converts datetimes to epoch ms. |
| 13 | `health` endpoint — does not check MongoDB | `GET /health` always returns `{"status": "ok"}` regardless of whether MongoDB is reachable. The spec says it must return 503 if MongoDB does not answer a ping, and the runner polls this before testing. | Killing MongoDB and calling `GET /health` still returns 200; the test runner proceeds and all tests fail with connection errors. | Added `db.command("ping")` inside a try/except; raises `HTTPException(503)` on failure. |

## Things I examined and decided were NOT defects

- **`compute_work_hours`**: The formula `round((punch_out - punch_in).total_seconds() / 3600, 2)` is functionally correct for basic cases, but Python's built-in `round()` uses banker's rounding (round-half-to-even) not ROUND_HALF_UP as required by R4/R8. I replaced it with a `round_half_up()` helper using `Decimal` to satisfy the spec exactly. This is arguably a defect but is subtle enough that it only surfaces on exact half-way values (e.g. 1.005 hours).
- **`IST = timezone(timedelta(hours=5, minutes=30))`**: Correct definition of the IST offset.
- **The Pydantic `EmployeeIn` and `PunchInIn` models**: The field names and types are correct. I extended them with validators for the epoch-ms range checks and status values that the spec requires.
